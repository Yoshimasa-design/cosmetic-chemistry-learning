# 変更履歴

## 文書情報

* 文書バージョン：Ver.0.1
* 更新日：2026-07-21
* 対象プロジェクト：化粧品素材から化学を学ぼう

---

# 1. 目的

本書は、プロジェクトにおける設計変更、仕様変更、重要な判断、および各バージョンの更新内容を記録するための文書である。

変更内容だけでなく、変更理由と影響範囲も記録し、後から開発経緯を確認できるようにする。

---

# 2. 記録対象

次の変更を記録対象とする。

* 教育コンセプトの変更
* 掲載素材の追加、削除、入替え
* データモデルの変更
* ID体系の変更
* 画面構成の変更
* 技術構成の変更
* 使用ライブラリの変更
* ディレクトリ構成の変更
* マイルストーンの変更
* バージョンの目的変更
* 公開範囲の変更
* 化学的内容の重要な修正
* 参考文献や根拠情報の変更
* 開発方針に影響する判断

誤字修正や軽微な表示調整は、必要に応じて簡略化して記録する。

---

# 3. 変更履歴の記録形式

各変更は、次の形式で記録する。

```text
## YYYY-MM-DD Ver.x.x

### 変更内容

変更した内容を記載する。

### 変更理由

なぜ変更したのかを記載する。

### 影響範囲

影響を受ける設計書、データ、画面、機能などを記載する。

### 対応状況

未対応、対応中、対応済みのいずれかを記載する。

### 関連コミット

Gitコミットのハッシュまたはコミットメッセージを記載する。
```

---

# 4. ステータス

変更への対応状況は、次の3種類とする。

| ステータス | 意味                        |
| ----- | ------------------------- |
| 未対応   | 変更方針は決定したが、設計書や実装へ反映していない |
| 対応中   | 設計書または実装の変更作業を進めている       |
| 対応済み  | 設計書、データ、実装への反映が完了している     |

## 2026-07-21 Ver.0.1

### 変更内容

本システムを化粧品成分辞典ではなく、化粧品素材を通して化学を学ぶ教育システムとして設計する方針を確定した。

基本学習経路を次のように定義した。

```text
化学構造
↓
物理化学的性質
↓
化粧品中での機能
↓
製剤中での役割
↓
製品
```

さらに、製品から化学構造へ遡る逆方向学習にも対応することとした。

### 変更理由

素材名や用途の暗記ではなく、「なぜその素材がその働きを示すのか」を理解できる教材とするため。

### 影響範囲

* 教育コンセプト
* データモデル
* 知識グラフ
* 画面構成
* 学習テーマ
* 比較機能
* 製品画面

## 2026-07-21 Ver.0.1

### 変更内容

素材データを単純な分類ツリーではなく、複数の分類軸で管理する方針を採用した。

主な分類軸は次のとおりとした。

* 主分類
* 化学分類
* 機能分類
* 由来

主分類では、次の区分を使用する。

* 単一化合物
* 高分子
* 混合物
* 抽出物
* 無機物

### 変更理由

化粧品素材には、単一化合物、高分子、天然油、抽出物、無機化合物などが含まれ、単一の分類方法では化学的特徴を適切に表現できないため。

### 影響範囲

* データモデル
* 素材一覧
* 検索
* 絞り込み
* 比較機能

# 6. 今後の記録方法

新しい変更は、この文書の上部または該当バージョンの先頭へ追記する。

原則として、新しい履歴を古い履歴より上に配置し、最新の変更を最初に確認できるようにする。

各バージョンの開発完了時には、少なくとも次の内容を記録する。

* 実装した機能
* 追加した素材
* 修正した設計
* 未解決の課題
* 次バージョンへの持越し事項
* Gitタグ
* 主要コミット

---

# 7. Gitとの対応

変更履歴へ記録した内容は、可能な限りGitコミットと対応させる。

コミットメッセージの例：

```text
Add Ver.0.1 project documentation
Define initial ingredient data model
Add knowledge graph design
Revise initial ingredient list
Implement ingredient detail page
Fix glycerin property data
```

リリース時にはGitタグを作成する。

例：

```text
v0.1.0
v0.2.0
v1.0.0
```

タグ作成後、対応するタグ名を変更履歴へ追記する。

---

# 8. 記録上の原則

1. 変更後の内容だけでなく、変更理由を残す。
2. 設計変更と実装変更を区別する。
3. 化学的な修正は、修正根拠も記録する。
4. 既存履歴を削除せず、訂正履歴を追加する。
5. Gitコミットだけに依存せず、重要な判断を文章として残す。
6. 将来の開発者が判断経緯を理解できる記述とする。
7. 未解決事項を隠さず記録する。
